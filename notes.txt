1. CORE PRINCIPLES: CI, CD, & ORCHESTRATION
================================================================================

* CI (Continuous Integration):
  - Automatically builds, lints, and tests your code every time you push
    changes to a remote Git repository (e.g., GitHub, GitLab).
  - Goal: Catch syntax errors, broken tests, and integration issues as early
    as possible before merging into the main branch.

* CD (Continuous Delivery vs Continuous Deployment):
  - Continuous Delivery: Code is automatically built, tested, and packaged into
    a deployment-ready artifact (e.g., Docker image). Production release requires
    a manual approval trigger.
  - Continuous Deployment: Every change that passes all automated test stages is
    deployed directly to production users automatically without manual approval.

* Kubernetes (K8s):
  - Acts as an orchestrator for containers across a cluster of servers.
  - Manages automatic scaling, self-healing (restarting crashed containers),
    load balancing, and zero-downtime rolling updates.

2. WORKFLOW AUTOMATION (YAML & GITHUB ACTIONS SYNTAX)
================================================================================

YAML File Location in Repo: .github/workflows/main.yml

--------------------------------------------------------------------------------
KEYWORD DEFINITIONS & CHEATSHEET
--------------------------------------------------------------------------------
* name: 
  - Defines the title of the workflow or individual job shown in GitHub UI.

* on:
  - Defines the event trigger that executes the pipeline.
  - Examples:
      on: [push, pull_request]
      on:
        push:
          branches: [main, staging]
          paths: ['server/**']

* jobs:
  - Container block holding all tasks to execute. Jobs run IN PARALLEL by default.

* runs-on:
  - Defines the runner OS host environment.
  - Examples: ubuntu-latest, windows-latest, macos-latest.

* steps:
  - A ordered, sequential list of commands or actions executed within a single job.

* run:
  - Executes raw terminal shell commands inside the runner environment.
  - Example: run: npm test

* uses:
  - Imports pre-built, reusable actions created by GitHub or community.
  - Example: uses: actions/checkout@v4

* with:
  - Passes parameters or options into an imported 'uses' action block.
  - Example:
      with:
        node-version: '20.x'

* env:
  - Injects environment variables for runtime execution.
  - Example:
      env:
        PORT: 5000
        DATABASE_URL: ${{ secrets.PROD_DB_URL }}

* needs:
  - Creates dependencies between jobs, forcing them to run SEQUENTIALLY.
  - Example:
      deploy:
        needs: [build, test]  # Wait for build & test jobs to pass first!


--------------------------------------------------------------------------------
FULL ANNOTATED EXAMPLE (MERN STACK MONOREPO CI)
--------------------------------------------------------------------------------
name: Fullstack MERN CI

on:
  push:
    branches: [main]

jobs:
  test-backend:
    runs-on: ubuntu-latest
    defaults:
      run:
        working-directory: ./server
    steps:
      - name: Checkout Source Code
        uses: actions/checkout@v4

      - name: Setup Node.js Runtime
        uses: actions/setup-node@v4
        with:
          node-version: '20.x'

      - name: Install Dependencies
        run: npm ci

      - name: Run Integration Tests
        run: npm test

  build-frontend:
    runs-on: ubuntu-latest
    defaults:
      run:
        working-directory: ./client
    steps:
      - name: Checkout Source Code
        uses: actions/checkout@v4

      - name: Setup Node.js
        uses: actions/setup-node@v4
        with:
          node-version: '20.x'

      - name: Build Production Assets
        run: npm run build

  deploy:
    name: Production Deployment
    needs: [test-backend, build-frontend]
    runs-on: ubuntu-latest
    steps:
      - name: Execute Deployment Script
        run: echo "Deploying tested application to cloud server..."

3. CONTAINERIZATION ESSENTIALS (DOCKER IN-DEPTH)
================================================================================

Why Docker?
- Solves "It works on my machine" by bundling application code, OS dependencies,
  system tools, and runtime configurations together into a self-contained unit.

* Core Concepts:
  - Dockerfile: A text file containing sequential instructions to build an image.
  - Docker Image: A read-only, immutable blueprint (class) containing dependencies.
  - Docker Container: A running isolated process (instance) spawned from an image. 
  - Docker Registry: A repository storing images (e.g., Docker Hub, GHCR, AWS ECR). --like what github is to Git
  - Docker Volume: Persistent storage detached from container lifecycle, ensuring 
    database files survive container restarts.
  - Docker Network: Manages internal/external communication between containers
    (e.g., API container talking to MongoDB on a private bridge network).



* Docker Multi-Stage Builds (Optimizing Production Image Size):
  Multi-stage builds allow compiling code in a heavy build environment and
  copying ONLY production artifacts into a minimal final runtime container.

  # --- Stage 1: Build Stage ---
  FROM node:20-alpine AS builder
    /app
  COPY package*.json ./
  RUN npm ci
  COPY . .
  RUN npm run build

  # --- Stage 2: Production Stage ---
  FROM node:20-alpine AS runner
  WORKDIR /app
  ENV NODE_ENV=production
  COPY package*.json ./
  RUN npm ci --only=production
  COPY --from=builder /app/dist ./dist
  EXPOSE 3000
  USER node
  CMD ["node", "dist/main.js"]

* Essential CLI Commands:
  - docker build -t my-app:v1 .        (Build image from Dockerfile)
  - docker run -d -p 8080:3000 my-app   (Run container detached, map host 8080 to container 3000)
  - docker ps                           (List running containers)
  - docker logs -f <container_id>       (Stream live logs)
  - docker exec -it <container_id> sh   (Open interactive shell inside container)
  - docker-compose up -d                (Launch multi-container stack from docker-compose.yml)

4. CONTAINER ORCHESTRATION (KUBERNETES FUNDAMENTALS)
================================================================================

When single-server Docker is not enough, Kubernetes manages container clusters across
multiple cloud virtual machines.

* Core Kubernetes Objects:
  - Pod: The smallest deployable unit in Kubernetes (wraps one or more containers).
  - Deployment: Manages state, replicas, scaling, and rolling updates for Pods.
  - Service: Exposes a set of Pods internally or externally with a stable IP address
    and built-in load balancer (Types: ClusterIP, NodePort, LoadBalancer).
  - Ingress: Configures HTTP/HTTPS routing rules to direct external web traffic to
    internal Services.
  - ConfigMap / Secret: Separates configuration data and encrypted credentials
    from container application code.


* Basic Deployment Manifest (deployment.yaml):
  apiVersion: apps/v1
  kind: Deployment
  metadata:
    name: saas-backend
  spec:
    replicas: 3
    selector:
      matchLabels:
        app: saas-backend
    template:
      metadata:
        labels:
          app: saas-backend
      spec:
        containers:
        - name: backend
          image: ghcr.io/my-org/backend:v1.2
          ports:
          - containerPort: 3000

9. DEPLOYMENT STRATEGIES & RELIABILITY
================================================================================


* Rolling Update: Replaces instances one-by-one with zero downtime.
* Blue / Green Deployment:
  - Spins up a brand new identical environment ("Green") alongside old ("Blue").
  - Tests green, then instantly flips network router traffic from Blue to Green.
* Canary Deployment:
  - Rolls out new code to a small percentage of users (e.g., 5% of traffic).
  - Monitors error rates automatically before rolling out to 100% of servers.
